# パシリ 🥐

近所のパン屋の買い物を、近所の「パシリ」さんが何人分かまとめて買って届けるサービスです（スマホ向け Web アプリ）。

- お客さん：店を選ぶ → 商品を選ぶ → 注文（カードは**仮押さえ**だけ）→ 進行状況 → 受け取り → 評価
- パシリ：近くの注文をまとめて引き受け → 買い物 → レシート撮影 → 配達 → 受け取りコード読み取り → 報酬が入金
- パン屋：商品・価格の登録、パシリ特典、注文の集計
- 運営：設定値の管理、アクセス台帳、通行記録、お金の台帳、トラブル対応

設計の詳しい説明は [docs/design.md](docs/design.md) にあります。

## 1. 動かしてみる（はじめての方向け）

### 必要なもの

- **Docker Desktop**（https://www.docker.com/products/docker-desktop/ ）
  インストールして起動し、画面左下が緑色（Engine running）になっていれば準備完了です。

### 起動（コマンド1つ）

このフォルダ（`pashiri`）でターミナル（PowerShell など）を開きます。

はじめての1回だけ、設定ファイルのひな形をコピーして `.env` を作ります（中身はそのままで動きます）。

```bash
copy .env.example .env
```

あとは次を実行します。

```bash
docker compose up --build
```

初回は数分かかります。`[起動時チェック] アクセス台帳とコードは一致しています` と表示されたら、ブラウザで **http://localhost:3000** を開いてください。

- 止める：ターミナルで `Ctrl + C`
- もう一度起動：`docker compose up`（データは残っています）
- データを全部消して最初からやり直す：`docker compose down -v` のあと `docker compose up --build`

> Stripe のキーを入れなければ、決済は**モック（偽物の Stripe）**で動きます。本物のカードやお金は一切使いません。

### テスト用のアカウント

起動時に、テスト用の店・商品・ユーザーが自動で入ります。パスワードはすべて **`pashiri-test-1234`** です。

> このパスワードは GitHub などで公開されています。そのため、テスト用データが入るのは次の3つがそろったときだけです。
> - `.env` に `SEED_TEST_DATA="true"` と書いてある
> - `APP_URL` が自分の PC（`http://localhost:3000` など）
> - Stripe の本番キーが入っていない
>
> 公開するサーバーで `true` のままにすると、起動時にエラーで止まります（気づかずにテストユーザーが入るのを防ぐため）。

| メールアドレス | 役割 | 使い方 |
|---|---|---|
| customer@example.com | お客さん（たろう） | 注文する |
| customer2@example.com | お客さん（はなこ） | 2人分まとめる練習に |
| runner@example.com | パシリ（はしるくん） | 注文を引き受けて届ける |
| both@example.com | お客さん＋パシリ（かねるさん） | 「自分の注文は引き受けられない」の確認に |
| shop@example.com | パン屋（こむぎ堂・ひなたベーカリー） | 商品・価格・特典・集計 |
| admin@example.com | 運営 | 設定値・台帳・トラブル対応 |

### 通しで試す手順（10分）

1. **お客さん**：`customer@example.com` でログイン → 「こむぎ堂」→ 商品を選ぶ → 受け渡し場所を入れて注文 → 「テストカードで支払う」
2. （別のブラウザ、またはシークレットウィンドウで）`customer2@example.com` でも同じ店で注文
3. **パシリ**：`runner@example.com` でログイン → 2つの注文にチェック → 報酬を確認して「まとめて引き受ける」
4. 買い物リストで実際の値段を入力（変えずに OK）→ レシートの写真（どんな画像でも可）を選んで登録 → 「届けた」
5. **お客さん**の注文画面に出る6桁の受け取りコードを、パシリの画面で入力 → 「受け取り完了」（本決済）
6. もう1人は、お客さん画面で「受け取りました」を押す（または放っておくと自動完了）
7. **パシリ**の「報酬」画面で入金済みになっていることを確認
8. **運営**：`admin@example.com` で「お金の台帳」→「いま照合する」で「差異なし」を確認

> 自動完了・入金・期限切れは、裏で動く「定期処理ワーカー」（worker）が30秒ごとに処理します。待たずに試したいときは、運営メニューの「定期処理をすぐ動かす」ボタンを押してください。

## 2. 設定値の変え方

金額・率・時間などの数字は、プログラムに直接書かず、すべて**設定値**として管理しています。

### 運用中に変える（ふつうはこちら）

1. `admin@example.com` でログイン → 運営メニュー →「設定値の管理」
2. 変えたい項目の「変える」→ 新しい値と**理由**を入れて「保存」
   - 範囲外の値（例：手数料率 0.9）は保存できません
   - 「どこに適用するか」で、**エリア別・店舗別**の上書きもできます（例：この店だけ立替上限を 8000円に）
3. 間違えたら、下の「変更履歴」から「この前の値に戻す」

**大事なルール**
- 変更は**これから作られる注文**から反映されます。
- **進行中の注文**は、注文したときの設定値（スナップショット）で最後まで計算されます。途中で金額が変わることはありません。
- 「立替上限」「まとめられる件数」は、引き受けるときの値が使われます（厳しくしたらすぐ効くように）。
- 変更はすべて履歴と通行記録に残ります。

### 初期値を変える

初期値は `config/settings.default.yaml` にあります。ここを変えても、**すでに DB に入っている値は変わりません**（運営が変えた値を守るため）。新しいキーを追加したときだけ反映されます。最初からやり直したいときは `docker compose down -v` で DB ごと消してください。

### 新しい設定キーを足すとき（開発者向け）

1. `config/settings.default.yaml` にキー・値・型・単位・説明・最小・最大を書く
2. `src/server/settings/definitions.ts` の `Settings` と `KNOWN_KEYS` に同じキーを足す（ずれていると起動しません）
3. コードでは `resolveForShop(shopId)` や注文の `settingsSnapshot` から読む（数字を直接書かない）

## 3. アクセス台帳（だれに何を許すか）の追加方法

「だれが・どの出入り口で・何を・どの範囲まで・どの項目を見られるか」は、すべて
[`security/access_ledger.yaml`](security/access_ledger.yaml) の1か所に書いてあります。

- **台帳に書かれていない出入り口・ロールは、すべて拒否されます。**
- コードと台帳がずれていると、**アプリは起動しません**（テストでも検出します）。
- 運営画面の「アクセス台帳」で一覧（全ロール × 全出入り口の表）を見られます。変更はこのファイルをコードレビューして行います。

### 例：お客さんが自分の注文のメモを変えられる API を足す

① 台帳に出入り口を足す

```yaml
  - id: api.customer.orders.update_note
    kind: api
    method: PATCH
    path: /api/customer/orders/:id/note
    resource: order          # :id の注文が「範囲内か」を門番が確かめる
    grants:
      - role: customer
        ops: [update]
        scope: own           # 自分の注文だけ
        fields: [id, note]   # 返してよい項目
        reason: 受け渡しのメモを直すため
```

② 処理を `src/server/endpoints/customer.ts` に足す（`id` を台帳と同じにする）

```ts
  endpoint({
    id: "api.customer.orders.update_note",
    input: z.object({ note: z.string().max(200) }),
    async handler(ctx) {
      return prisma.order.update({ where: { id: ctx.params.id }, data: { note: ctx.input.note } });
    },
  }),
```

権限チェックは書きません。ログイン確認・ロール・CSRF・入力チェック・範囲（`own`）・返す項目の絞り込み・通行記録は、すべて共通の門番（`src/server/gate/dispatch.ts`）がやります。

③ `npm test` で確認（台帳に足し忘れると「台帳にありません」で失敗します）

画面を足すときは `kind: page` の行を足します（`src/app/.../page.tsx` と1対1）。

## 4. Stripe（テストモード）で動かす

モックではなく、本物の Stripe のテスト環境で試すときの手順です。お金は動きません。

1. https://dashboard.stripe.com/register でアカウントを作り、**テストモード**にする
2. 「Connect」を有効にする（ダッシュボードの Connect → 始める）
3. `.env.example` をコピーして `.env` を作り、次を入れる
   ```
   PAYMENT_MODE="stripe"
   STRIPE_SECRET_KEY="sk_test_..."
   STRIPE_PUBLISHABLE_KEY="pk_test_..."
   ```
4. Webhook を受け取るために Stripe CLI（https://docs.stripe.com/stripe-cli ）を入れて、別のターミナルで実行
   ```bash
   stripe listen --forward-to localhost:3000/api/webhooks/stripe
   ```
   表示された `whsec_...` を `.env` の `STRIPE_WEBHOOK_SECRET` に入れる
5. `docker compose up --build`
6. パシリは「報酬」→「受け取り口座」から Stripe の登録画面（テスト用の値で OK）を済ませる
7. お客さんの支払い画面ではテストカード `4242 4242 4242 4242`（有効期限は未来、CVC は任意）

> `sk_live_` / `pk_live_`（本番キー）を入れると、アプリは起動を拒否します。

## 5. テスト

Docker で DB が動いている状態で（`docker compose up db` だけでも OK）：

```bash
npm install
npm test
```

- `tests/unit` … 報酬計算（純粋な関数）、状態遷移、台帳の形式チェック、起動時チェック、項目の絞り込みなど（DB 不要：`npm run test:unit`）
- `tests/integration` … 本物の門番と DB を使った、通しの流れ・不正操作・二重決済・設定値スナップショット・台帳の改ざん防止のテスト

テストは専用の DB（`pashiri_test`）を毎回作り直して使います。開発用のデータは消えません。

## 6. フォルダの中身

| 場所 | 中身 |
|---|---|
| `config/settings.default.yaml` | 設定値の初期値 |
| `security/access_ledger.yaml` | アクセス台帳 |
| `docs/design.md` | 設計書（データモデル・状態遷移・お金の流れ） |
| `prisma/` | DB の定義・マイグレーション・テスト用データ |
| `src/server/gate/` | 門番（台帳との照合・範囲・項目の絞り込み・通行記録） |
| `src/server/domain/` | 業務ルール（報酬計算・状態遷移・注文の流れ） |
| `src/server/payments/` | 決済（Stripe / モック、冪等な与信・本決済・送金） |
| `src/server/money/` | お金の台帳（複式簿記） |
| `src/server/jobs/` | 定期処理（自動完了・期限切れ・送金・照合） |
| `src/server/endpoints/` | API の処理（台帳の id と1対1） |
| `src/app/` | 画面 |
| `tests/` | テスト |

## 7. 本番公開前チェックリスト

このアプリは**テストモード専用の試作品**です。本番で使う前に、少なくとも次を確認してください。

### 法令・契約（専門家に必ず確認すること）
- [ ] **資金の流れが法令上問題ないか、弁護士など専門家に確認する。** 本アプリは Stripe Connect の「Separate charges and transfers」方式で、お客さんの支払いを Stripe 上で受け、パシリの Connect アカウントへ送金します。運営の銀行口座をお金が通らない設計ですが、資金決済法（資金移動業・前払式支払手段）や収納代行の扱い、割賦販売法などの評価は専門家の判断が必要です。
- [ ] パシリとの契約形態（業務委託など）、労働法・税務（報酬の源泉徴収・支払調書）
- [ ] 特定商取引法に基づく表記、利用規約、プライバシーポリシー（個人情報保護法）
- [ ] 食品を扱う上での衛生・責任範囲（パン屋・パシリ・運営）
- [ ] Stripe の利用規約・Connect の審査（日本のプラットフォームとして利用できる形か）

### セキュリティ
- [ ] `APP_SECRET` を十分に長いランダムな値にする。`.env` をリポジトリに入れない
- [ ] HTTPS で公開する（`APP_URL` を `https://...` にすると Cookie に Secure が付きます）
- [ ] 信頼できるリバースプロキシの後ろに置き、`X-Forwarded-For` をプロキシが上書きするようにする（ログイン回数制限と通行記録の IP に使っています）
- [ ] 開発用の「メールの代わりにログへ確認リンクを出す」処理（`src/server/endpoints/auth.ts`）を、本物のメール送信に差し替える。SMS 認証・二段階認証も検討する
- [ ] `.env` の `SEED_TEST_DATA` を `false` にする（テスト用ユーザーを本番 DB に入れない。もし入っていたら削除する）
- [ ] 最初の運営（admin）アカウントの作り方を決める（テスト用データを入れないと admin はいません）
- [ ] DB のバックアップ。通行記録・お金の台帳は追記専用なので、保存期間と容量の方針を決める
- [ ] DB ユーザーの権限を分ける（アプリ用のユーザーからトリガーを外せないようにする）
- [ ] レシート画像の保存先をクラウドの非公開ストレージ（S3 など）にし、保存期間を決める
- [ ] 依存パッケージの脆弱性チェック（`npm audit`）、第三者によるセキュリティ診断
- [ ] 運営アカウントの数を最小にし、個人情報の閲覧記録を定期的に確認する

### お金
- [ ] Stripe のテストモードで、与信・本決済・解放・送金・返金・Webhook の再送をひととおり確認
- [ ] 与信（仮押さえ）の有効期限（カードによって約7日）より、注文〜受け取りの時間が十分短いこと
- [ ] 毎日の照合で差異が出たときの連絡先と対応手順を決める
- [ ] パシリへの送金後に返金が必要になったときの手順（Stripe ダッシュボードで Transfer の取り消し → 返金。アプリの画面からは送金前の返金だけできます）
- [ ] 設定値（手数料率・報酬・上限など）の初期値を、実際の運用に合わせて決め直す

### 運用
- [ ] 定期処理ワーカー（worker）が止まったときに気づける監視
- [ ] 通行記録の異常検知（短時間の大量拒否）を定期的に見る担当
